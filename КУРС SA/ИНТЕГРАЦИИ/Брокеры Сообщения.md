# Сравнение RabbitMQ vs Kafka

RabbitMQ — это классический брокер с push-моделью, отличной маршрутизацией и низкой задержкой. Подходит для фоновых задач и микросервисов с умеренной нагрузкой. 

Kafka — распределённый лог событий с pull-моделью, долгосрочным хранением и очень высокой пропускной способностью. Используют для стриминга, аналитики и когда нужно перечитывать историю событий

| Аспект             | RabbitMQ                                                                                                           | Apache Kafka                                                                                                       |
| ------------------ | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| Тип                | классический брокер                                                                                                | стрим событий/логов                                                                                                |
| Модель доставки    | умный брокер - глупый получатель <br>- брокер сам решает маршрут кому что отдать<br>-получатель берет то, что дали | глупы брокер - умный получатель<br>- брокер хранит версии и лог <br>- получатель сам выбирает что и когда получать |
| Хранение сообщений | временно ограниченно(удаляется после получения)                                                                    | долгосрочно (по указанию)                                                                                          |
| Повторное чтение   | после получения удаляется из очереди                                                                               | можно, сохраняются логи                                                                                            |
| Производительность | +                                                                                                                  | +++                                                                                                                |
| Маршрутизация      | гибкая по типу exchanges -**Direct** - **Fanout** - **Topic** - **Headers**                                        | простая по ключу в партиции                                                                                        |

Его главная задача — принимать сообщения от одного сервиса (producer), надёжно хранить их и доставлять другому сервису (consumer), при этом позволяя очень гибко маршрутизировать сообщения.

Producer → Exchange → (по правилам binding/routing) → Queue → Consumer (брокер сам толкает сообщение потребителю).

![[{6A068C05-BDE0-4106-A646-E1A21F650051}.png]]
### Основные компоненты RabbitMQ

| **Producer**        | - приложение, которое **отправляет** (publish) сообщение.                                                                                        |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Exchange**        | - «почтовый ящик» или точка входа. Producer отправляет сообщение именно в exchange, а не напрямую в очередь.                                     |
| **Queue** (очередь) | - место, где хранятся сообщения до тех пор, пока их не заберёт consumer. Очереди могут быть **durable** (сохраняются после перезапуска брокера). |
| **Consumer**        | -  приложение, которое **получает** и обрабатывает сообщение.                                                                                    |
| Binding             | - правило, которое связывает exchange с очередью (и часто с routing key).                                                                        |
| **Routing key**     | - метка/ключ, по которому exchange решает, в какую очередь положить сообщение.                                                                   |


**Типы exchanges** - 4 основных
1. **Direct** — сообщение идёт в очередь, если routing key **точно совпадает**.
2. **Fanout** — сообщение рассылается **во все** связанные очереди (broadcast, игнорирует routing key).
3. **Topic** — гибкая маршрутизация по шаблонам с wildcard (* и #), например: logs.error.critical, logs.*.eu.
4. **Headers** — маршрутизация по заголовкам сообщения (не по ключу, а по набору атрибутов).

**Когда используют RabbitMQ** (типичные сценарии для BA):
- Фоновые задачи (отправка email, обработка фото, генерация PDF)
- Микросервисы с умеренной нагрузкой
- Сложная маршрутизация (например, разные типы уведомлений разным командам)
- Задачи с приоритетами и подтверждениями доставки (acknowledgments)
- RPC-подобное взаимодействие (request → reply)

RabbitMQ — это **"умный брокер, глупый потребитель"**: брокер сам решает маршрутизацию, а потребитель просто берёт то, что ему дали.



# Apache Fakfa
платформа потоковой обработки событий), а не просто message broker.

Producer → Topic (разделён на partitions) → Consumer сам забирает данные, когда готов (pull). Сообщения не удаляются после прочтения — они остаются до конца retention периода.

| **Producer**    | - отправляет события в topic.                                                                                                                                     |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Broker**      | - сервер Kafka (в кластере их много).                                                                                                                             |
| **Topic**       | - категория/канал событий (аналог папки или ленты).                                                                                                               |
| **Partition**   | - topic делится на несколько партиций (для параллелизма и масштаба). Сообщения с одинаковым ключом всегда попадают в одну и ту же партицию → порядок сохраняется. |
| **Offset**      | - номер позиции в партиции (consumer запоминает, до какого offset он прочитал).                                                                                   |
| **Replication** | - каждая партиция имеет копии (replicas) на разных брокерах для отказоустойчивости.                                                                               |
| **Retention**   | - события хранятся заданное время (по умолчанию 7 дней, но можно годами).                                                                                         |
| **Consumer**    | - читает события из topic. Потребители могут объединяться в **consumer groups** (для параллельной обработки).                                                     |

**Когда используют Kafka** (самые частые сценарии):
- Высоконагруженные потоки событий (миллионы сообщений/сек)
- Real-time аналитика и мониторинг (логи, метрики, поведение пользователей)
- Event sourcing / CQRS
- Change Data Capture (CDC) — отслеживание изменений в БД
- Долгосрочное хранение событий для replay (перечитывания истории)
- Интеграция с big data (Spark, Flink, ELK и т.д.)

Kafka — это **"глупый брокер, умный потребитель"**: брокер просто хранит лог, а потребитель сам решает, что и когда читать.
